# vng regression suite — plan

Goal: a pass/fail suite that runs the **real yserver** (KMS, renderer, input,
VT) in a vng guest, locally and in CI, so a release can be cut without
major regressions. Branch `feat/ci-vng-lavapipe`.

## Where we are (2026-09-30)

- `tools/vng-shot.sh` boots yserver in a vng guest and runs a scenario;
  about twenty scenarios exist in `tools/vng-scenarios/`, most of them
  writing logs that were compared by hand against an Xorg run.
- `--gpu none` (`122ad957`): 2D virtio-gpu with `blob=on` + lavapipe, no
  host GPU. yserver takes the legacy-linear scanout route; measured equal
  to Venus in speed (xterm 12 s, xrandr-scale 22 s, span-paint 2 outputs /
  10 rounds 81 s, xrandr-rotate 49 s) and results. Needs `/dev/kvm` and
  `/dev/udmabuf` usable (udev `MODE="0666"`).
- virtme-ng passes `accel=kvm:tcg`: an unusable `/dev/kvm` silently falls
  back to TCG (every run in this session before the sandbox fix did).

## Phase 0 — harness hygiene (`tools/vng-shot.sh`)

1. **Isolation.** Drop `--rw`: the host root is read-only in the guest with
   a discarded overlay; only the artifact directory is writable
   (`--rwdir`). Scenarios run as a throwaway user `ysuite` created in the
   guest with a tmpfs home, so no run reads or writes the host user's
   configuration (a Cinnamon run once left `cinnamon-monitors.xml` behind).
   - Environment of `ysuite`: fresh `HOME`, fresh `XDG_CONFIG_HOME`,
     `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `XDG_STATE_HOME` and a private
     `XDG_RUNTIME_DIR` (0700), its own session bus (`dbus-run-session`).
   - Privilege split: yserver runs as root in the guest (DRM master,
     input); every client, WM and desktop runs as `ysuite`. The artifact
     directory is created by the guest root and made writable by `ysuite`;
     the host reads it after the run.
2. **KVM or fail.** Check the guest ran under KVM (guest dmesg
   "Hypervisor detected: KVM") and fail the run otherwise.
3. **Relative mouse.** `-machine vmport=off`: under KVM the guest gets a
   VMware VMMouse that ignores QEMU's relative `mouse_move`, so
   `pointer-*-host.sh` no longer moves the pointer on either server.
4. **lavapipe ICD path** overridable (Arch `lvp_icd.json`, Ubuntu possibly
   `lvp_icd.x86_64.json`).

## Phase 1 — runner

- `tools/vng-suite.sh` + `just vng-suite [filter] [gpu]`: runs every
  scenario (or a filter) one at a time, per-scenario timeout, prints a
  result table, exits non-zero on any failure, keeps artifacts of failures
  under `target/vng-suite/<run>/`.
- Scenario metadata (a small header block per scenario): guest script,
  optional host driver, output count, timeout, required gpu mode(s).
- **The host runner decides the result**, not the guest: guest assertions
  write `RESULT` (`pass` / `fail: <reason>`) into the artifact directory,
  and the host combines it with host-side assertions (pixel checks done
  outside the guest, e.g. `xrandr-rotate-scanout-host.sh`, which today
  prints mismatches without failing), server health (yserver still alive at
  the end, no crash/abort, no GPU fault in the log) and timeout status.
  Missing `RESULT`, a timeout or a dead server ⇒ fail.
- Cleanup: on pass, fail, timeout or Ctrl+C the runner stops and reaps that
  run's own guest and helper processes (recorded pids only, never
  `pkill`), so no VM or watcher outlives the run.
- The runner is itself tested: a deliberately failing assertion, a
  deliberately crashed server, a scenario that hangs past its timeout, and
  an interrupted run must each be reported as fail and leave nothing
  running.
- `--binary <path>` is passed through (run against an already-built
  binary), and a filter that selects no scenario is an error.
- Every run records the yserver commit, gpu mode, KVM status, and the
  kernel, Mesa, QEMU and virtme-ng versions alongside the results.

## Phase 2 — self-asserting scenarios

Convert the existing scenarios so each checks its own outcome:

- **Pixel checks use an independent expectation, not scanout vs root
  GetImage:** those two agree when both carry the same defect (the stale
  background and cursor trails seen on 2026-09-30). The oracle is a
  generated pattern: the scenario sets a known patterned root background
  (and known window contents), applies the layout change (scale, rotate,
  second output, partial updates), moves the cursor repeatedly, and checks
  every output's scanout — including every rectangle the cursor vacated —
  against the pattern pushed through the CRTC matrix.
- **Goldens** are the measured Xorg 21.1.24 values. They are regenerated by
  running the same scenario with `--server xorg`
  (`tools/vng-suite.sh --regen-goldens <scenario>`) and stored as small text
  files next to the scenario (`tools/vng-scenarios/goldens/<name>.txt`),
  reviewed like code. No images in the repo: pixel checks compare against
  an expectation computed at run time (root GetImage pushed through the
  CRTC matrix, a known fill colour, …).
- Normalise what legitimately differs (XIDs, mode ids, atom numbers,
  timestamps, known pre-existing divergences listed per scenario).
- First batch: `xrandr-scale`, `xrandr-scale-crop`, `xrandr-dpi`,
  `xrandr-monitors`, `xrandr-rotate`, `xrandr-orientation`,
  `xrandr-scale-cursor`, `span-paint`, `pointer-scale`/`pointer-rotate`,
  `record`, `xi2-raw-keys`, `xmodmap-caps-control`, `xkbcomp-upload`.
- New bugs get a scenario as part of their fix (as `span-paint` did).

## Phase 3 — desktops

One scenario per desktop: awesome, XFCE, MATE, Cinnamon, Plasma, openbox.

- Session: `dbus-run-session` + `gnome-keyring-daemon --unlock` (empty
  password) in the `ysuite` home, so apps do not stall on a missing keyring
  (bare sessions manufacture hangs, e.g. the one-minute PrintScreen delay).
- Checks: WM up (`_NET_SUPPORTING_WM_CHECK`), panel/desktop mapped; a
  scripted round (terminal, a GTK and a Qt app; move, resize, maximise,
  focus, close via `xdotool`/`wmctrl`, geometry and focus asserted); a
  known wallpaper pattern checked in the scanout after each layout change
  and after cursor movement (the independent oracle above). All pixel
  checks are automatic — no human or agent looks at images: the scenario
  sets the wallpaper to the generated pattern through the DE's own setting
  (`gsettings … picture-uri`, `xfconf-query`, …), masks what may cover it
  (window and panel rectangles from `_NET_CLIENT_LIST`, struts,
  `xwininfo`), and compares every visible wallpaper pixel with the pattern
  (exact for nearest scaling, a small tolerance for bilinear). Subtle
  look-and-feel defects in panels/widgets stay with the physical smoke
  test; yserver alive, no GPU fault; no `WARN`/`ERROR` in
  `yserver.log` beyond a per-desktop allowlist.
- DE-specific: Cinnamon/MATE fractional scaling and rotation (the #185/#189
  sequences), XFCE compositor on/off, KWin compositing in Plasma.

## Phase 4 — CI

- **Feasibility first**, before converting the desktops: one small scenario
  (xterm + one pixel check) on the chosen `ubuntu-latest` image, proving
  that `/dev/kvm` and `/dev/udmabuf` actually work there (not just their
  permissions), the guest runs under KVM, and lavapipe + blob scanout come
  up. GitHub calls nested virtualisation on hosted runners experimental, so
  this is an actual run, not a reading of the docs.
- GitHub workflow on `ubuntu-latest`: udev rule for `/dev/kvm` and
  `/dev/udmabuf`, `apt install virtme-ng qemu-system-x86
  mesa-vulkan-drivers xterm x11-xserver-utils xdotool python3-xlib
  python3-pil` (+ desktops), a guest kernel with virtio-gpu/drm
  (`linux-image-generic` + `linux-modules-extra`, `KERNEL=`), `--gpu none`.
  Artifacts of failing scenarios uploaded.
- PRs: phase-2 scenarios + awesome and XFCE. Nightly or on demand:
  everything.
- If Ubuntu's desktop packages diverge too much from what we ship against,
  switch to a prebuilt Arch rootfs image (desktops + `ysuite`) booted with
  `vng --root`, cached between runs.

## Phase 5 — release gate

`just release-check`: the whole suite locally on silence in both gpu modes
plus the existing gates (fmt, clippy, workspace tests, lavapipe
`--ignored`). Both gpu modes still exercise *virtual* display hardware, so
the release gate keeps a separate **physical KMS smoke test** on real
hardware (silence and bee: scanout, direct scanout, PRIME, HW/SW cursor,
two outputs, rotation/scaling). A release is cut only when both are clean.

## Open issues before trusting results

- **Venus root captures corrupt under KVM** (`xrandr-rotate`: ~1.5 % of rows
  correct, rest black/garbled; clean under `--gpu none`, and clean under
  Venus while runs were on TCG). Suspect: coherency of Venus host-visible
  mappings with the host-cached readback buffer (#184). Real hardware
  screenshots are clean. Until explained, pixel checks gate on
  `--gpu none` only.
- `pointer-scale` needs phase-0 item 3 before it can assert anything.
- Venus mode logs validation-layer errors on dma-buf external-memory image
  creation (`vkCreateImage`/`vkBindImageMemory`); `--gpu none` logs none.
  Allowlist or fix before Venus runs are gated on a clean log.
